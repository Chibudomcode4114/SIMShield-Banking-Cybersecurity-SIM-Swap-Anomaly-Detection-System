1. Purpose and Design Logic
This reusable prompt converts the Day 3 lecture and progressive lab guide into one controlled agentic implementation run. It starts from the student’s validated product mission and working service topology, then makes the product visible without pretending that later data, RAG, model or production capabilities already exist.
LECTURE REQUIREMENT
AGENTIC IMPLEMENTATION CONTROL
Continue Days 0–2
Trace every route, actor, state and visible promise to the G1 mission and Day 2 boundaries.
Adapt—not copy—AcademGPT
Transfer reusable patterns while replacing its domain, actors, terminology, data and rules.
Design all actors; build a bounded slice
Inventory every validated actor, then implement the primary actor and one accountable oversight role.
Make failures visible

Use UI as architecture
Turn every visible data need and action into a classified, owned backend-contract backlog item.
Prove usability

Protect programme sequencing

CORE PRINCIPLE  •  A screen is a bundle of obligations: actor, job, permission, state, evidence, owner and failure behaviour.

6. Non-Negotiable Operating Rules
Inspect before changing. Inventory the repository, current branch, uncommitted changes, Nuxt structure, package scripts, UI dependencies, Day 2 configuration and health status before editing.
Preserve student work. Never reset, delete, overwrite or reorganize unrelated files. Merge carefully or create a clearly named sibling when a meaningful conflict exists.
Stay inside scope. Work only in the authorized project directory and only on Day 3 interface architecture, implementation, verification and evidence.
Do not replace the Day 2 topology. Nuxt remains the browser experience; browser-facing product requests are designed for NestJS. Never connect the frontend directly to MySQL, Weaviate or FastAPI.
Use the existing package manager and compatible project conventions. Do not switch package managers, mass-upgrade dependencies or introduce a heavy UI framework unless the repository already uses it or the student explicitly approves a justified exception.
Use Vue 3, TypeScript, Nuxt 4, Pinia, vanilla CSS and the existing $fetch boundary. Prefer small reusable components and modular feature stores.
Protect secrets and privacy. Never expose or commit credentials. Do not place real personal, confidential or regulated data in mocks, screenshots, logs, videos or evidence.
Use deterministic, contract-shaped synthetic data. Random output that cannot reproduce a state is not valid evidence.
Make assumptions visible. Mark every dependency on unfinished Day 1 or Day 2 work as [PROVISIONAL] with reason, owner, recovery action, evidence required and deadline.
Do not pretend later capabilities exist. Retrieval, generation, live queues, persistence and audit may be represented through typed interfaces and mocks, but must be labelled as simulated until verified in their programme phase.
Ask only blocking questions. Group questions when missing information would materially change actors, privacy, authorization, destructive action or architecture. Otherwise choose the safest bounded assumption and record it.
Verify by execution. Build, test, start and inspect the UI. Do not claim usability, accessibility or route protection solely from code review or screenshots.
Repair safely. Diagnose from evidence, make the smallest reversible change and rerun the exact failed check.
Stop at control boundaries. Pause for direction if completion would require a destructive action, public deployment, paid service, new credentials, sensitive-data exposure or expansion beyond the approved G1 scope.
Required interaction style
Start with a compact discovery summary, proposed plan, readiness lane and blockers.
Share short progress updates at meaningful milestones, including when a skill, fallback or provisional dependency changes the plan.
Explain decisions in plain language and name the evidence that supports them.
Continue through implementation, verification, safe repair and evidence generation. Do not stop after planning or scaffolding.
Finish with the exact evidence-backed response contract in Section 20.

10. Phase C — Create the Complete Actor–View Inventory
Inventory every validated actor before implementing feature depth. Use authentic domain role names; do not default to Student, Advisor, Admin or Auditor unless those roles genuinely exist. Student, Advisor, and others are just used here for demonstration sake.
For each actor, record responsibility, dashboard purpose, maximum three priority actions, permitted knowledge/data, prohibited access, priority journey, oversight/escalation, required states, evidence/confidence needs, implementation depth and acceptance task.
Record read, write, approve, assign, export and policy-change capabilities separately. Frontend visibility is not server authorization; create corresponding BFF enforcement items.

11. Phase D — Design Information Architecture, Journeys and State
Create a role-scoped navigation map with global, primary, contextual, utility and recovery navigation. Every route needs an actor permission, entry point, current-location cue and safe onward/recovery action.
Ensure the primary job is reachable without exploring the application. Define mobile navigation and prevent orphan screens.
Model each priority journey as Trigger → Orient → Act → Wait → Decide → Recover/Escalate → Confirm.
Create a state matrix for loading, empty, error, denied, escalated and success. Add domain-specific states such as stale, conflicted, reassigned or resolved when needed.
For each state record the trigger, plain-language message, preserved context, allowed next action, forbidden action, responsible owner and evidence to capture.
Create low-fidelity wireframes for every actor and detailed wireframes for the primary and oversight journeys before high-polish implementation.
STATE
REQUIRED USER ANSWER

12. Phase E — Establish the Shared Nuxt 4 Design System and Shell
Adapt the existing Nuxt application; do not replace the Day 2 baseline. Use the repository’s established conventions where compatible with the programme stack.
Create or refine shared vanilla-CSS tokens for dark surfaces, text hierarchy, borders, accent, success, warning, danger, spacing, typography, shape, focus, interaction and responsive layout.
Create semantic application regions: header, role-scoped navigation, main content, contextual status and recovery/help. Use meaningful headings, links, buttons, form labels and landmarks.
Render navigation from typed actor capabilities. A development-only role/state switcher may be used for testing only if it is clearly labelled and protected from release builds.
Create reusable components for state notices, status, evidence/citations, limitations, form feedback and accessible dialogs before adding decorative polish.
Define desktop, tablet and narrow-mobile behaviour. Preserve the primary action and evidence; transform wide tables deliberately rather than shrinking them beyond usability.
Respect reduced-motion preferences, high zoom/reflow and non-colour status cues. Avoid hover-only explanations.
Keep styles in the shared vanilla-CSS system. Do not introduce a utility framework or component library solely to accelerate appearance.

13. Phase F — Model Typed UI State and Integration Boundaries
Use modular Pinia feature stores for session/active actor, navigation and the selected domain journey. Keep raw credentials and server-authoritative RBAC out of client state.
Define typed interfaces for every visible record, status, source, limitation, feedback item and escalation. Map each visible element to a typed field or intentional interface-only value.
Create three to five deterministic, contract-shaped, privacy-safe scenarios that can force the happy path, no-evidence/empty path, service error, denied path and escalation path.
Provide a predictable development-only state harness or test fixture. Random data and unreproducible screenshots are not acceptable.
Preserve the Day 2 browser-to-NestJS configuration and $fetch boundary. If a real BFF endpoint exists and is safe, use it behind a typed adapter; otherwise use a deterministic mock adapter labelled [PROVISIONAL].
Do not call FastAPI, MySQL or Weaviate directly from the frontend. Add every intended server enforcement, persistence, retrieval, generation or real-time obligation to the contract backlog.
Make switching between mock and later real adapters explicit and environment-controlled without exposing internal service names or secrets to the browser.
14. Phase G — Implement the Primary Actor Journey
Create a dashboard that identifies the actor, current scope and priority job without exposing technical service topology.
Allow the actor to begin one bounded domain task with guidance, validation and permission context.
Show honest progress, preserve submitted context and prevent duplicate action.
Present the answer, recommendation, extraction or classification in task-oriented language with evidence, limitations, freshness and an intelligible quality/confidence signal where justified.
Offer only safe next actions: accept, correct, compare, save, retry, give feedback or escalate, according to the approved mission.
Confirm the resulting status, accountable owner and next step in history or status UI.
Demonstrate all five mandatory variants: representative success with accessible evidence; insufficient/no evidence without fabrication; service failure with preserved context and controlled retry; permission denied without protected preview; and escalation with reference, owner class, status and expected next step.
15. Phase H — Implement the Oversight Journey
Use the oversight role named by the domain. The reference pattern is an Advisor/HITL queue, but role titles and permissible decisions must come from the G1 operating model.
Show prioritised assigned or unassigned items with reason, age/freshness and safe actor context.
Open an item to show the original request, scoped evidence, generated or derived output, limitation, relevant history and escalation trigger.
Allow only authorised decisions; require a rationale where the operating model demands it; make consequences visible before confirmation.
Prevent stale, reassigned, unauthorised, duplicate or already-resolved decisions even in the simulated state model.
Update status visibly and show the primary user an access-safe outcome while keeping protected reviewer notes private.
Represent future persistence, audit and real-time behaviour as explicit contract items; do not imply they are already operational.
